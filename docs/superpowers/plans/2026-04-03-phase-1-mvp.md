# Kubri Dashboard — Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Kubri Dashboard MVP — a multi-tenant web app for Italian social cooperatives and employment agencies to view, filter, and manage candidate profiles from the Kubri AI chatbot.

**Architecture:** Hybrid data architecture — PostgreSQL (Supabase) for auth, orgs, notes, tags, audit logs; Make.com Data Store API (read-only) for candidate profiles. Each org has its own Make.com Data Store. All candidate data access goes through a caching + normalization integration layer.

**Tech Stack:** Next.js 14+ (App Router), TypeScript strict, Tailwind CSS, shadcn/ui, Prisma, Auth.js v5, in-memory LRU cache, @react-pdf/renderer, pnpm, Vercel.

**Resolved Decisions:**
- Auth: Auth.js v5 with Credentials provider (email+password)
- DB: Supabase PostgreSQL
- Cache: In-memory LRU (`lru-cache`) — upgrade to Upstash Redis later if needed
- Make.com: One Data Store per org (separate `datastore_id` + `api_token` per org)
- Token encryption: AES-256-GCM via Node.js `crypto`, `ENCRYPTION_KEY` in env
- Testing: Vitest (unit/integration) + Playwright (E2E)

---

## Context

The Kubri chatbot already runs on Telegram via Make.com. Candidate data is stored in Make.com Data Stores. Today, organizations receive candidate profiles as static Excel/PDF files on Google Drive — no browsing, no filtering, no multi-tenancy. This dashboard replaces that workflow.

The hybrid architecture is temporary (Phase 2 migrates candidate data to PostgreSQL), so the Make.com integration layer must be well-isolated and replaceable.
