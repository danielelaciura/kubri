# Location Proximity Filter — Design

**Date:** 2026-05-01
**Status:** Approved (brainstorming)

## Goal

Add a proximity-based location filter to the candidates page and to job
descriptions, leveraging the existing `latitude`/`longitude` fields on
candidate records (Make.com Data Store) and a new lat/lng extension of the
local `ITALY_ADMIN` table.

Two user-facing surfaces:

1. **Candidates page** — operators pick a place and a radius (km) to find
   candidates near a chosen location.
2. **Job Description form** — when creating/editing a JD, the operator picks
   the location (as today) and additionally sets a **default search radius**
   that is persisted on the JD. This radius will be the default starting
   point for proximity searches launched from that JD in a future phase.

Out of scope for this phase: launching a proximity candidate search directly
from a JD detail page (the "Trova candidati vicini" button), Google Places
integration, sub-municipality granularity, EU coverage.

## Architectural decisions

- **Geocoding source: extend `ITALY_ADMIN`.** No external API. Static dataset
  only. Italy-only, granularity = municipality / province / region. Zero
  runtime cost. Justification: aligned with the current Italian market
  focus, reuses the existing combobox infrastructure, and avoids billing /
  API-key management complexity.
- **Coordinates are NOT denormalized onto JDs.** The JD keeps storing
  `locationMunicipality` / `Province` / `Region` as strings; coordinates are
  resolved at query time via `resolvePlaceCoords`. The only new column on
  `JobDescription` is `searchRadiusKm`.
- **Proximity filtering happens application-side.** Candidate records live in
  Make.com Data Store; we cannot push a haversine query down. After fetching
  + caching the candidates as today, we apply `filterByRadius` in memory.
  Acceptable given current volume.

## Data

### `ITALY_ADMIN` (extended)

Each row gets two new fields:

```ts
interface ItalyAdminRow {
  municipality: string;
  province: string;
  region: string;
  latitude: number;
  longitude: number;
}
```

Source: ISTAT public dataset of Italian municipalities with coordinates.
For province/region rows, use the centroid (or capoluogo) coordinates so
that selecting "Lombardia" yields a usable center point.

The dataset is regenerated by a one-shot build script (committed output).
The script is documented but not run in CI.

### PostgreSQL — `JobDescription`

New column:

```
searchRadiusKm  Int  NOT NULL  DEFAULT 25
```

Migration name: `add_jd_search_radius`.
Constraints (validated in Zod, not at the DB): 1 ≤ value ≤ 200.

### Make.com Data Store

No change. `latitude` / `longitude` are already present on candidate
records (PR #4).

```ts

  a: { latitude: number; longitude: number },
  b: { latitude: number; longitude: number },

export function resolvePlaceCoords(
  label: string,

// Lookup priority: exact municipality → province → region.
// Normalization via existing normalizePlace from lib/geo/resolve.

export function filterByRadius<T extends { latitude: number | null; longitude: number | null }>(
  items: T[],
  center: { latitude: number; longitude: number },
  radiusKm: number,
): T[];
// Items with null coords are excluded when the filter is active.
```

## UI changes

### Candidates page — filter panel

`src/components/candidates/candidate-filters.tsx`:

- New section "Vicino a..." inside the expanded filter panel, alongside the
  existing `Lingue` / `Paese di origine` / `Città` fields.
- Two controls:
  - `LocationCombobox` bound to a `nearPlace` state.
  - `Slider` (shadcn) bound to `radiusKm` state, range 1–200, step 5,
    default 25. Visible only when `nearPlace` has a value.
- The current value is shown next to the slider (e.g. "25 km").
- The existing `city` text filter stays — it's a different filter (substring
  match on `preferred_location`).
- On apply, both values go into the URL: `?nearPlace=Milano&radiusKm=25`.
- Reset clears both.

### Candidates page — server

`src/app/(dashboard)/dashboard/candidates/page.tsx`:

- Read `nearPlace` and `radiusKm` from `searchParams`.
- If `nearPlace` is set:
  - Resolve via `resolvePlaceCoords(nearPlace)`.
  - If the resolution returns `null`, treat the filter as inactive (no-op,
    optionally surface a soft warning later — not in this phase).
  - Otherwise apply `filterByRadius` to the fetched candidate list before
    pagination.
- Pagination is computed on the post-proximity list. The total count thus
  reflects the filtered set, which is acceptable for current volumes.

### JD form

`src/components/jobs/job-form.tsx`:

- Below the `LocationCombobox`, add a `Slider` "Raggio di ricerca default"
  with the same range/step/default as above.
- Display current value (e.g. "25 km") next to the slider.
- Submitted as `searchRadiusKm` in the form data.

### JD validations & actions

`src/lib/validations/job-description.ts`:

```ts
searchRadiusKm: z.coerce.number().int().min(1).max(200).default(25)
```

`src/app/(dashboard)/dashboard/jobs/actions.ts` and
`.../jobs/[id]/actions.ts`:

- Read `searchRadiusKm` from the FormData and pass it through to the
  service / Prisma create/update.

### JD detail page

`src/app/(dashboard)/dashboard/jobs/[id]/page.tsx`:

- Display the saved radius next to the location (e.g. "Milano · 25 km").
- No proximity-search button in this phase.

## Tests

### Unit

- `src/__tests__/lib/geo/proximity.test.ts`
  - `haversineKm`: known city pairs (Milano–Roma ≈ 477 km tolerance ±5),
    identical points → 0.
  - `resolvePlaceCoords`: exact municipality hit, province hit, region hit,
    miss returns `null`, case/diacritics insensitivity (via `normalizePlace`).
  - `filterByRadius`: items inside / on edge / outside, items with `null`
    coordinates excluded.
- `src/__tests__/lib/geo/italy-admin.test.ts`
  - Every row has `latitude` ∈ [-90, 90] and `longitude` ∈ [-180, 180].
  - No duplicate `(municipality, province)` keys.
- `src/__tests__/lib/validations/job-description.test.ts`
  - `searchRadiusKm` accepts 1, 25, 200.
  - Rejects 0, 201, non-integer, negative.
  - Defaults to 25 when omitted.

### Integration

- `src/__tests__/lib/jobs/service.test.ts`
  - Create JD persists `searchRadiusKm` (provided value and default).
  - Update JD changes `searchRadiusKm`.
- Candidate page filter test (mock Make cache layer): when `nearPlace` and
  `radiusKm` are set, only candidates within the radius are returned.

## Migration & rollout

Per CLAUDE.md migration workflow:

1. `pnpm prisma migrate dev --name add_jd_search_radius`
2. Implement code, write tests, commit migration + code together.
3. Apply to prod **before merge** with `prisma migrate deploy` against
   `.env.prod`.
4. Verify with `prisma migrate status`.
5. Merge → Vercel auto-deploys.

The default of 25 covers existing rows safely.

## Risks / notes

- **Region/province centroids are coarse.** Selecting "Lombardia" + radius
  10 km will include very few candidates because the centroid sits near
  Milano. This is acceptable: regions and provinces are mostly used as
  filter labels, while real proximity searches will use municipalities.
- **Application-side filtering scales linearly** with the cached candidate
  list. Fine at current volumes (hundreds to low thousands per org), would
  need a server-side index when migrating candidate data to PostgreSQL
  (Phase 2 — out of scope).
- **Place resolution misses are silent in this phase.** A surfaced warning
  in the UI when `resolvePlaceCoords` returns `null` is a follow-up.
